# API integration guide

- **Status:** Current overview
- **Owner:** API maintainers
- **Last reviewed:** 2026-08-03
- **Review trigger:** Route, authentication, versioning or error-contract change

The interactive OpenAPI documentation is available at `/docs` when the API is running.
This guide explains integration behavior that is easy to miss when reading individual
endpoints.

## Base path

Versioned application routes use:

```text
/api/v1
```

Health and readiness routes may use separate paths according to the application
configuration.

## Authentication

### Local demonstration

Local mode requires explicit demonstration identity. The portal supplies the configured
demo user. Manual API calls require the documented development identity headers.

Development headers must not be enabled in shared environments.

### OIDC

Shared environments use a bearer access token. The API validates the token and derives
a stable principal and capabilities. The frontend does not send simulated identity
headers in Entra mode.

## Authorization model

Authorization is resource- and action-specific. Common rules include:

- only the initiative owner or administrator can edit a draft;
- reviewers need the governance area required by the gate;
- the owner cannot approve the owner's own scope;
- system and asset mutation belongs to the relevant owner or administrator;
- model and agent review use different independent areas;
- emergency administrative operations require explicit authority.

A successful authentication does not imply permission to perform a governance action.

## Optimistic concurrency

Mutable resources carry a version. Commands that alter governed state require the
client's expected version.

A stale version should produce a conflict response instead of silently overwriting a
newer state. Clients should:

1. read the latest resource;
2. send the current expected version;
3. handle conflict by refreshing and presenting the difference;
4. avoid blind automatic retries for decisions.

## State transitions

Clients should use explicit action endpoints or commands for transitions such as:

- submit for review;
- request changes;
- resubmit;
- approve or reject;
- review model or agent scope;
- retire an asset;
- block or restore access;
- create or resolve an incident.

Do not infer state by directly updating a status field.

## Evidence uploads

Clients must:

- use an allowed file type;
- respect the configured maximum size;
- expect temporary service unavailability while the malware scanner is not ready;
- not depend on internal bucket or object-key fields;
- treat an external reference separately from a verified uploaded artifact.

Uploads are not safe to retry blindly after an ambiguous network failure unless the API
exposes or adopts a stable idempotency mechanism.

## Error handling

Applications should distinguish:

| Category | Client behavior |
|---|---|
| Authentication failure | Obtain a valid token; do not retry unchanged credentials indefinitely |
| Authorization denial | Explain missing capability; do not hide as generic server error |
| Validation error | Correct the request payload |
| Not found | Confirm identifier and access context |
| Version conflict | Refresh resource and require user reconciliation |
| Invalid state transition | Refresh and follow the allowed workflow |
| Dependency unavailable | Retry only according to operation semantics and backoff policy |
| Internal failure | Preserve correlation ID and alert operators |

## Correlation and audit

Integrations should provide or preserve a correlation ID when supported. Business
systems should store the governance entity ID and decision reference rather than only a
human-readable name.

Audit events are generated by the application; clients must not be allowed to provide
arbitrary audit identities or hashes.

## Pagination and filtering

When list endpoints support pagination:

- use bounded page sizes;
- follow application-generated cursors or offsets;
- do not trust user-provided external pagination URLs;
- use stable filters and identifiers for reconciliation.

## Idempotency guidance

Read operations are idempotent. Not all writes or external routing calls are safe to
repeat. Before adding automatic retries, classify the operation:

- pure update guarded by expected version;
- creation with a client-provided idempotency key;
- irreversible decision;
- external call with a persisted pending/final state;
- evidence upload with ambiguous completion.

## Integration checklist

- [ ] Use the correct authentication mode.
- [ ] Resolve user/service identity through approved claims.
- [ ] Preserve expected versions.
- [ ] Handle conflict and invalid-state responses explicitly.
- [ ] Minimize payload data.
- [ ] Use stable entity IDs.
- [ ] Preserve correlation IDs.
- [ ] Define retry and timeout behavior per operation.
- [ ] Store decision references and policy versions when needed.
- [ ] Test negative authorization paths.
