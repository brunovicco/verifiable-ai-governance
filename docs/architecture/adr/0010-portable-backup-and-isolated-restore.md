# ADR 0010 - Portable backup and isolated restore

## Status

Accepted.

## Date

2026-08-01.

## Context

PostgreSQL holds decisions, snapshots, evidence metadata, and the audit trail.
Evidence bytes live in private object storage. Protecting only one of these services
produces an incomplete restore: records can point to missing objects, or objects can
lose their context, owner, and retention.

Compose already preserves volumes and blocks API startup until the explicit
migration runs, but a persistent volume is not a backup. The stale-schema incident
documented in ADR 0009 also showed the need to prove recovery without altering the
primary database.

## Decision

We will adopt a portable logical package for the reference environment, made up of:

- a custom-format PostgreSQL dump generated by `pg_dump`, without ownership or
  privileges;
- a copy of all objects in the private bucket via the S3 API;
- an immutable, versioned manifest with provenance, Alembic revision, counts, sizes,
  and SHA-256;
- a checksum separate from the manifest to detect accidental corruption;
- creation in a private temporary directory and atomic publication;
- verification by recomputing hashes and reading the catalog through `pg_restore`;
- restore only into a database and bucket that do not already exist;
- a restore test against randomly chosen isolated targets, with state comparison and
  cleanup.

The flow depends on ports owned by the application layer. Adapters implement the
local filesystem, PostgreSQL tools via Compose, and an S3-compatible service. The CLI
only composes these dependencies and reads configuration from the environment.

Since PostgreSQL and S3 do not share a transaction, capture requires a write-free
window or an equivalent quiesce mechanism. In production, managed services may
replace the adapters, provided they preserve consistency, integrity, and restore
assurance.

## Alternatives considered

- Copy only the Docker volume: rejected for not being portable, depending on the
  image layout, and not demonstrating logical recovery.
- Back up only PostgreSQL: rejected because it would exclude the evidence bytes.
- Back up only the bucket: rejected because it would lose context, authorization,
  and the audit trail.
- Restore over the original database and bucket: rejected due to the risk of
  destruction and the impossibility of validating before cutover.
- Consider the checksum sufficient against tampering: rejected; it detects
  corruption, but authenticity requires an external control, immutability, or
  signing.

## Consequences

The project now has a reproducible path for capturing, verifying, and recovering
both backing services. The manifest allows explaining and auditing the content
without exposing data in the command output.

The package can be large, the restore test temporarily duplicates storage, and
consistent capture requires operational coordination. The format will need to
evolve compatibly as new backing services are added.

## Security and privacy impact

The package contains personal data, confidential information, and evidence. Local
files and directories get restrictive permissions, object keys and content are not
logged, and credentials come from the environment. Paths, target names, sizes, and
hashes are validated before use.

SHA-256 does not encrypt or authenticate against coordinated substitution. Real
backups must use encryption, separate key management, least privilege, retention,
disposal, immutability, and storage outside the failure domain. Location, support,
and international copies feed into the international-processing assessment.

## Operational impact

Operations must monitor the age of the last valid backup and the last tested
restore, capacity, duration, failures, and cleanup of temporary targets. RPO and RTO
remain organizational decisions based on risk.

Restore does not apply migrations beyond the captured state. Promotion happens
through configuration and cutover after a smoke test and approval, preserving the
origin for rollback.

## Follow-up

- Integrate the procedure with a scheduler and production alerts.
- Define RPO, RTO, retention, and frequency per risk tier.
- Add manifest signing or attestation in the corporate environment.
- Test managed backup adapters and versioned object storage.
- Record periodic results as operational-control evidence.
