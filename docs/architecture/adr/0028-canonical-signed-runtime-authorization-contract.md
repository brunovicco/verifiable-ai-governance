# ADR 0028 - Canonical signed runtime authorization contract

## Status

Accepted.

## Date

2026-08-07.

## Context

Governance currently evaluates initiatives, reviews models and agents, computes
runtime scope, enforces local routing boundaries and persists routing evidence.

The next integration step must carry that authorization across process and
repository boundaries:

```text
Verifiable AI Governance
    -> Policy Model Router
    -> Multi-Agent Credit Desk
```

Passing only an agent ID or a Boolean `approved=true` would force downstream
services either to trust mutable caller assertions or to duplicate Governance
database access.

A portable authorization artifact must therefore bind the approved scope, the
exact runtime request and the policy provenance that produced the decision.

## Decision

Define a vendor-neutral v1 envelope with three top-level members:

```json
{
  "protected": {},
  "claims": {},
  "signature": "..."
}
```

The bytes signed by P1.2 are the canonical JSON serialization of:

```json
{
  "protected": {},
  "claims": {}
}
```

The signature itself is not included in the signed bytes.

### Protected header

The protected header binds:

- media type;
- `Ed25519` as the v1 algorithm;
- key identifier (`kid`).

`kid` is covered by the signature. Consumers must never select a key from
unprotected metadata.

### Claims

Claims bind:

- unique authorization ID;
- issuer;
- one or more audiences;
- `issued_at`, `not_before` and `expires_at`;
- initiative, AI system and agent identity/version;
- the approved agent review digest;
- the P0.4 runtime `scope_digest`;
- exact workflow, task and workload;
- context/output token estimates;
- structured-output requirement;
- latency and cost bounds;
- risk and data classification;
- authorized model IDs, versions, routing groups and review digests;
- tool and permission allowlists;
- runtime duration bound;
- human approval points;
- kill-switch availability;
- governance policy and control-catalog identity, version and digest.

### Replay boundary

The artifact is request-scoped rather than session-scoped.

`workflow_id`, `task_id`, workload and request constraints are signed. Reusing the
artifact for a different task or budget changes the signed payload and must fail
verification or downstream claim comparison.

### Lifetime

Contract v1 permits at most 600 seconds between `issued_at` and `expires_at`.
Issuers may choose a shorter lifetime.

All timestamps must be expressed explicitly in UTC.

### Canonical JSON profile

The contract deliberately avoids floating-point numbers in signed claims. Monetary
values are represented as integer USD micros.

Canonical serialization uses:

- UTF-8;
- lexicographically sorted object keys;
- no insignificant whitespace;
- no NaN or Infinity;
- normalized sorted set-like collections;
- canonical UUID strings;
- UTC ISO-8601 timestamps generated by Pydantic JSON mode.

This profile is intentionally narrower than general JSON and makes equivalent
contract values produce identical signing bytes across implementations.

## Why not JWT

JWT/JWS would be a viable transport, but v1 does not need browser identity,
OAuth claims or JOSE algorithm agility. A small explicit JSON envelope:

- keeps governance-specific claims visible;
- avoids accidental acceptance of unrelated JWTs;
- avoids algorithm-confusion defaults;
- makes the exact signed bytes easy to demonstrate;
- remains portable across Python, Go, Java and TypeScript.

The envelope borrows the useful protected-header property from JWS without
declaring itself to be a JWT.

## Why Ed25519

P1.1 reserves only Ed25519 for contract v1 because it provides:

- small keys and signatures;
- deterministic signatures;
- strong library support;
- simple verification semantics;
- no RSA padding or ECDSA nonce configuration.

P1.1 does not generate or verify signatures. Cryptographic implementation belongs
to P1.2.

## Fail-closed rules for consumers

P1.2 consumers must reject an artifact when any of these checks fail:

- unsupported media type or schema version;
- unsupported algorithm;
- unknown or inactive `kid`;
- invalid signature;
- issuer mismatch;
- audience mismatch;
- authorization not yet valid or expired;
- duplicate/replayed authorization ID where replay protection is required;
- request facts differ from signed claims;
- current Governance scope digest differs from the signed `scope_digest` when a
  fresh revalidation is available;
- selected model is not one of the signed model bindings;
- requested tool, permission or budget exceeds the signed scope.

## Consequences

- P1.2 can focus on key management, signing and verification instead of revisiting
  claim semantics;
- Policy Model Router and Credit Desk can consume the same contract;
- audit records can store the authorization ID, `kid`, scope digest and signing
  payload hash without storing prompts or customer content;
- policy and catalog upgrades become visible in authorization provenance;
- contract evolution requires a new schema version rather than silently changing
  v1 signing semantics.

## Security and privacy impact

The authorization contains identifiers, control metadata, limits and digests. It
contains no prompt, response, document, credentials, personal data or model
output.

Authorization artifacts are bearer-like security material even though they do not
contain secrets. Logs should record identifiers and digests, not the complete
envelope by default.

## Follow-up

- P1.2 implement Ed25519 signing, key rotation and verification;
- P1.3 require the verified authorization in Policy Model Router;
- P1.4 emit standardized violation events with authorization provenance;
- P1.5 propagate authorization and trace context through Credit Desk and
  `a2a-otel-kit`.
