# ADR 0045: Live Governed Runtime Actuation E2E

- Status: Accepted
- Date: 2026-08-09

## Context

P1.8 proved that real Credit Desk terminal evidence can drive deterministic Runtime Assurance,
explicit Incident promotion, and advisory runtime-response recommendations without automatic
actuation.

P1.9a through P1.9d then introduced a governed control lifecycle:

```text
recommendation
-> engage request
-> independent approval
-> engage execution
-> remediation
-> restore request
-> new independent approval
-> restore execution
```

Unit, application, endpoint, and boundary tests prove each local contract. A remaining gap is a
repeatable live proof that these contracts work together with the existing Runtime Control and
model-routing enforcement boundaries.

## Decision

Add P1.9e as a verification-only stage.

P1.9e adds no production domain model, API, migration, or actuator. It provides a live harness,
pure harness tests, an operations guide, and this ADR.

The live scenario must use real:

- Credit Desk A2A execution;
- a2a-otel-kit sanitized telemetry;
- Governance Runtime Assurance;
- Incident promotion;
- P1.9a/b/c/d HTTP contracts;
- Runtime Control projection;
- Policy Model Router routing decisions.

## Enforcement proof

Reading `kill_switch_engaged=true` is insufficient as the primary enforcement proof.

P1.9e must demonstrate observable behavior through the model-routing boundary:

```text
before engage: fresh routing -> ALLOWED via Policy Model Router
while active:  fresh routing -> BLOCKED / kill_switch_engaged
post restore:  fresh routing -> ALLOWED via Policy Model Router
```

This proves the Runtime Control state is consumed by a real runtime authorization boundary.

## Governed-path-only rule

The P1.9e harness must not call legacy direct actuation endpoints, including direct Runtime Control
activate/deactivate commands or Incident kill-switch engage/restore commands.

All state changes exercised by P1.9e must originate through:

```text
P1.9a request
P1.9b decision
P1.9c execution
P1.9d restore request
P1.9d restore decision
P1.9d restore execution
```

A boundary test enforces this restriction statically.

## Separation of Duties proof

The live test uses distinct principals:

```text
requester/executor != Security approver
```

It must explicitly prove self-approval is rejected for both engagement and restoration.

The engage and restore decision digests must also be distinct. Engage approval is historical lineage
for restore, never restore authorization.

## Idempotency proof

The live scenario replays:

- actuation request;
- engage approval;
- engage execution;
- restore request;
- restore approval;
- restore execution.

Equivalent replay must return the same evidence. Execution replay must not increment Runtime Control
transition count.

## Remediation proof

Restore eligibility must be created through the normal Incident remediation-plan API. The report
stores only the Incident ID/status/version and restore remediation digest, never the remediation
narrative itself.

## Evidence and privacy

The report is written to:

```text
artifacts/e2e/p1.9-governed-actuation-live-report.json
```

Only a curated structural projection is persisted. The telemetry secret is explicitly rejected if it
appears in serialized evidence.

The report is generated by the live run and is not fabricated as part of the implementation patch.

## Consequences

### Positive

- P1.9 becomes demonstrable as an integrated governed control lifecycle.
- Runtime enforcement is proven behaviorally, not inferred from database state.
- Separation of Duties and independent restore authorization are demonstrated live.
- Retry/idempotency properties are exercised across actual HTTP and persistence boundaries.
- The result can support a short architecture/demo walkthrough.

### Trade-offs

- The proof requires local Governance, Redis, Policy Model Router, and Credit Desk processes.
- Runtime-authorization signing/trust configuration must already be valid as established in P1.6.
- The harness deliberately refuses automatic cleanup because that would create an alternate control
  path outside the governance evidence chain.

## Non-goals

P1.9e does not:

- introduce new runtime actions;
- change production authorization policy;
- modify P1.9 digest formats;
- add a generic actuator;
- automate Security approval;
- introduce break-glass restore;
- call an LLM for governance decisions;
- replace P1.6 TOCTOU/replay verification;
- fabricate a successful live report.

## Follow-up

After P1.9e, the P1.9 governed containment/restore block is considered complete. Subsequent work can
focus on packaging the integrated demo and deeper cross-repository deployment/observability evidence
without broadening the runtime-control authority model.
