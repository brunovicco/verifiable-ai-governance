```text

   ↓

   ↓

   ↓
P1.8a deterministic Runtime Assurance
   ↓

   ↓
```

## Expected assurance evidence

The harness configures:

```text
evaluation_sample_size = 2
minimum_samples = 2
max_failure_rate = 0
breach_severity = critical
```

The real producer emits one terminal success and one terminal failure. The fresh
bounded sample must therefore yield:

```text
sample_count = 2
failure_count = 1
failure_rate = 0.5
outcome = breached
breach_reasons = [failure_rate_exceeded]
severity = critical
```

The evaluation must reference exactly those two fresh telemetry event IDs.

## Expected response evidence

The canonical demo Agent must begin with:

```text
kill_switch_enabled = true
kill_switch_engaged = false
```

The recommendation must contain:

```text
investigate_failures
prepare_containment
consider_kill_switch
```

and `advisory_only = true`.

## Zero-actuation proof

The harness snapshots and compares:

- Incident ID/status/severity/version;
- Agent ID/version/kill-switch availability/state;
- count of Runtime Control transitions.

All remain unchanged across recommendation generation.

This comparison begins after explicit P1.8b incident promotion because incident
creation or severity escalation is a valid P1.8b governed mutation; P1.8c advice is
not.

## Reruns

Reruns append new evidence and may increment the Runtime Assurance policy version.
An existing active incident may make promotion `deduplicated`; that is valid.

The harness never deletes or closes prior evidence merely to force a particular
promotion disposition.
